# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

`flow-py-sdk` is an async Python SDK for the Flow blockchain. It speaks gRPC to Flow Access Nodes using `grpclib` + `betterproto` v2 (beta). Public surface is exported from `flow_py_sdk/__init__.py`: `flow_client`, `AccessAPI`, `entities`, `Tx`, `ProposalKey`, `TxSignature`, `TransactionStatus`, `Script`, signers, `cadence`, etc.

Python 3.9+, managed with Poetry.

## Commands

All Python tooling runs through Poetry.

```sh
# Install deps
poetry install

# Run the whole test suite
poetry run pytest

# Run a single test file / class / case
poetry run pytest tests/test_get_transaction_result_by_index.py
poetry run pytest tests/test_get_transaction_result_by_index.py::TestGetTransactionResultByIndex
poetry run pytest tests/test_get_transaction_result_by_index.py::TestGetTransactionResultByIndex::test_passes_correct_parameters_to_stub

# Regenerate gRPC stubs from proto/ into flow_py_sdk/proto/
make generate

# Run examples against the Flow emulator (emulator must be running on localhost:3569,
# and examples/flow.json must contain an "emulator-account" entry — see examples/common/config.py)
poetry run examples            # runs all examples
poetry run examples <Name>     # runs a specific example by class name

# Build / serve docs
poetry run mkdocs serve
poetry run mkdocs build
```

When to run `make generate`: only after editing files under `proto/`. The generated output under `flow_py_sdk/proto/flow/` is committed but must never be hand-edited — every file in there starts with `# Generated by the protocol buffer compiler.  DO NOT EDIT!`.

## Architecture: two-layer design

Understanding the SDK requires reading three layers together (`proto/*.proto`, `flow_py_sdk/proto/flow/**`, `flow_py_sdk/client/{client.py,entities.py}`).

### Proto sources vs generated stubs

- `proto/flow/access/access.proto` and `proto/flow/entities/*.proto` are **vendored copies** of the upstream Flow protocol definitions from `https://github.com/onflow/flow/tree/master/protobuf/flow`. They are not hand-authored here — when the upstream API changes, copy the new `.proto` files in and regenerate.
- `flow_py_sdk/proto/flow/{access,entities,execution,legacy}/__init__.py` are the betterproto-generated Python stubs. The grpc service stub lives in `flow_py_sdk/proto/flow/access/__init__.py` as `class AccessApiStub(betterproto.ServiceStub)`.
- The upstream flow repo is already cloned locally at `/Users/vishal/go/src/github.com/onflow/flow` — copy from `flow/protobuf/flow/access/access.proto` and `flow/protobuf/flow/entities/*.proto` into `proto/flow/` here.

### betterproto v2 calling convention (CRITICAL)

This is the single most important fact in this repo. The generated stub methods take a **request message object positionally**, not keyword arguments. Calls written the old way will fail at runtime (or silently send the wrong request) even though they may type-check.

Correct:

```python
response = await super().get_latest_block(GetLatestBlockRequest(is_sealed=is_sealed))
response = await super().get_transaction_result_by_index(
    GetTransactionByIndexRequest(block_id=block_id, index=index)
)
```

Wrong (do not do this):

```python
response = await super().get_latest_block(is_sealed=is_sealed)            # broken
response = await super().get_transaction_result_by_index(block_id=..., index=...)  # broken
```

Also note the class name: betterproto renamed `AccessAPIStub` to `AccessApiStub` (lowercase `pi`). `AccessAPI` in `client.py` inherits from `AccessApiStub`. When patching in tests, target `AccessApiStub`.

### AccessAPI wrapper pattern

Every method in `flow_py_sdk/client/client.py` follows the same three-step shape:

1. Build the typed proto request object.
2. Call the inherited stub method via `super().<method>(request)`.
3. Convert the proto response to a hand-written entity via `entities.<Class>.from_proto(...)`.

Example (verbatim from `client.py`):

```python
async def get_latest_block(self, *, is_sealed: bool = False) -> entities.Block:
    response = await super(AccessAPI, self).get_latest_block(GetLatestBlockRequest(is_sealed=is_sealed))
    return entities.Block.from_proto(response.block)
```

The wrapper layer exists to (a) give users keyword-only Python-friendly kwargs, (b) accept flexible input types (e.g. `get_account` accepts `bytes | cadence.Address | str` and calls `cadence.Address.convert_to_bytes`), and (c) hide proto dataclasses behind hand-written entity classes.

Quirk: the generated method names contain stutters from the proto names — `get_block_by_i_d`, `get_collection_by_i_d`, `execute_script_at_block_i_d`, `get_events_for_block_i_ds`. The wrapper methods preserve these names, and the docs reference them as-is (e.g. `::: flow_py_sdk.AccessAPI.get_block_by_i_d` in `docs/api_docs/client.md`). Do not "fix" them.

### Entity layer

`flow_py_sdk/client/entities.py` contains hand-written Python classes (`Account`, `BlockHeader`, `Block`, `Collection`, `Transaction`, `TransactionResultResponse`, `EventsResponseResult`, `SendTransactionResponse`, `GetNetworkParametersResponse`, ...). Each defines a `@classmethod from_proto(cls, proto, ...)` that takes the generated proto dataclass and returns a user-facing object. This is the boundary that lets the proto layer be regenerated freely without breaking user code.

Some `from_proto` methods accept extra kwargs that aren't on the proto message — for example `TransactionResultResponse.from_proto(response, id=id)` lets `get_transaction_result` thread the transaction id through (the proto response doesn't echo it back).

## Testing

Tests live in `tests/` and use stdlib `unittest` (run via `pytest`). There is no live network in CI — live verification is done manually against `access.mainnet.nodes.onflow.org:9000` or `access.devnet.nodes.onflow.org:9000`.

- Sync tests: `unittest.TestCase`.
- Async client tests: `unittest.IsolatedAsyncioTestCase`.

The async client test pattern patches the stub method on the parent class with `AsyncMock`, constructs an `AccessAPI` with a `MagicMock()` channel, calls the wrapper, then asserts both the returned entity and the request object passed into the stub. The request-object assertion is what catches the betterproto calling convention going wrong:

```python
from unittest.mock import AsyncMock, MagicMock, patch
from flow_py_sdk.client.client import AccessAPI
from flow_py_sdk.proto.flow.access import AccessApiStub, GetTransactionByIndexRequest
from flow_py_sdk.proto.flow.access import TransactionResultResponse as ProtoTransactionResultResponse
from flow_py_sdk.proto.flow import entities as proto_entities

class TestGetTransactionResultByIndex(unittest.IsolatedAsyncioTestCase):
    async def test_passes_correct_parameters_to_stub(self):
        block_id = bytes.fromhex("ab" * 32)
        proto_response = ProtoTransactionResultResponse(
            status=proto_entities.TransactionStatus.PENDING, status_code=0,
            error_message="", events=[],
        )
        client = AccessAPI(channel=MagicMock())
        with patch.object(
            AccessApiStub, "get_transaction_result_by_index",
            new=AsyncMock(return_value=proto_response),
        ) as mock_stub:
            await client.get_transaction_result_by_index(block_id=block_id, index=5)
            mock_stub.assert_called_once_with(
                GetTransactionByIndexRequest(block_id=block_id, index=5)
            )
```

Note the assertion: `assert_called_once_with(GetTransactionByIndexRequest(block_id=..., index=...))` — a single positional request object, **never** kwargs. A unit test that asserts kwargs would pass against a wrapper that calls the stub the wrong way, and then silently break against a live node. The request-object assertion is what makes the test load-bearing.

When the response entity carries data not present in the proto message (e.g. the tx id passed through `get_transaction_result`), test both the default case and the explicit-id case — see `TestTransactionResultFromProto` in `tests/test_get_transaction_result_by_index.py`.

`tx_test.py` is a different shape: it tests RLP encoding of `Tx` against known-good hex strings, no mocks needed.

## Documentation

Docs are mkdocs + mkdocs-material + mkdocstrings.

- `docs/api_docs/client.md` is a thin shell of `::: flow_py_sdk.AccessAPI.<method>` directives. mkdocstrings reads docstrings off the live Python objects and renders them.
- Docstrings on `AccessAPI` methods use NumPy format (`Parameters`, `Returns` sections with `name : type` lines). Match the existing style — mkdocstrings parses it.
- `docs/python_SDK_guide.md` is the prose guide with usage snippets per topic.
- `mkdocs.yml` controls the nav; new API doc pages must be added there.

When adding a new client method, both files need a new entry: the `:::` directive in `docs/api_docs/client.md` under the appropriate H2 (Blocks / Accounts / Transactions / Events / Collections / Scripts), and a worked example in `docs/python_SDK_guide.md`.

## Adding a new Access API method (recipe)

1. **Update protos.** Copy `protobuf/flow/access/access.proto` and any changed `protobuf/flow/entities/*.proto` from `/Users/vishal/go/src/github.com/onflow/flow/protobuf/flow/` into this repo's `proto/flow/`. Do not edit them by hand.
2. **Regenerate.** `make generate`. Confirm the new request/response classes and the new stub method appear in `flow_py_sdk/proto/flow/access/__init__.py` (the stub class is `AccessApiStub`).
3. **Import the new request class** at the top of `flow_py_sdk/client/client.py`.
4. **Add the wrapper** on `AccessAPI`. Keyword-only args, build the request object, `await super().<method>(RequestClass(...))`, then `return entities.X.from_proto(response.<field>)`. If the response is a list (events, results), wrap with a list comprehension over the proto items.
5. **Add or extend the entity** in `flow_py_sdk/client/entities.py` with a `from_proto` classmethod when the response shape is new. If reusing an existing entity, no entity change is needed.
6. **Write tests** in `tests/` using the `AsyncMock` + `assert_called_once_with(RequestClass(...))` pattern above. Cover both happy path and a non-default field on the response.
7. **Document it** by adding `::: flow_py_sdk.AccessAPI.<method_name>` to `docs/api_docs/client.md` under the right section, and a usage example to `docs/python_SDK_guide.md`.

## Examples runner

`poetry run examples` is wired through `pyproject.toml`'s `[tool.poetry.scripts]` to `examples.main:run`. Each example is a class that subclasses `Example` and registers itself. They read connection settings from `examples/flow.json` (`emulator-account` key) via `examples/common/config.py` — defaults are `localhost:3569` if the file is missing. Examples expect a running Flow emulator.
